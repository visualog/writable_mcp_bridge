# 자료별 판단

## 1. `실제 작동방식 확인된 내용인거야? 추론 한거야?`
이 문서는 **가장 건강한 문서**야.

좋은 점:
- 스스로 `확인된 사실 / 추론 / 확인 불가`를 분리함
- Buddy 내부 구현을 확정적으로 말하지 않음
- “우리가 아는 것과 모르는 것”의 경계를 제일 정직하게 다룸

내 판단:
- 이 문서는 **기준 문서**로 쓰기 좋다.
- 앞으로 Buddy 관련 논의에서 이 문서의 분류 기준을 계속 유지하는 게 맞다.

---

## 2. `Buddy가 Figma를 읽고 쓰는 방식 — 기술적 심층 분석`
이 문서는 **방향은 좋지만, 확정처럼 읽히는 추정이 많이 섞여 있다**.

좋은 점:
- Buddy를 `READ / WRITE / DS 통합 / 샌드박스 제약`으로 나눈 구조는 매우 좋다.
- xbridge 엔진 설계에 필요한 관점을 잘 담고 있다.
- 특히
  - selection/tree read
  - design system scan
  - postMessage 구조
  - action execution
  이 네 축으로 정리한 건 유용하다.

하지만 조심할 점:
- `LLM이 Plugin API 코드를 생성하고 eval() 실행한다`
- `Claude Sonnet 4.6이 구체적으로 이런 코드 형태를 반환한다`
- `Retry design system 오류의 내부 원인`
이런 부분은 **공개 자료로 확인된 사실이 아니라 추정**이야.
- 문장 톤이 다소 단정적이라, 읽는 사람이 “이미 확인된 내부 구조”로 오해하기 쉽다.

내 판단:
- 이 문서는 **설계 힌트 문서**로는 좋다.
- 하지만 “Buddy 내부 구현 설명서”로 쓰면 위험하다.

## 3. `deep-research-report.md`
이 문서는 **가장 넓고 풍부하지만, 그만큼 추정이 사실처럼 섞인 비율도 높다**.

좋은 점:
- 아키텍처, API 활용, 통신, AI 모델, 보안, 성능, 실패 모드, 테스트 전략까지 폭넓게 다룸
- xbridge의 장기 방향성 잡을 때 참고할 재료가 많다
- 특히 “무엇을 테스트해야 하는가” 부분은 실제로 도움이 된다

하지만 약점:
- 아래 항목들은 공개 근거만으로는 강하게 말하기 어렵다
  - 서버가 WebSocket/SSE를 쓸 가능성
  - OAuth/JWT/임시 토큰 방식
  - 델타 업데이트, 캐싱, 옵티미스틱 UI
  - diff 비교, saveVersionHistoryAsync 활용
  - 구체적인 backoff 전략
- 즉, **좋은 엔지니어링 상상력**은 있지만 **Buddy에 대해 실제로 확인된 것**은 아니다.

내 판단:
- 이 문서는 `Buddy 사실 보고서`보다
- **“Buddy를 참고해 우리가 어떤 엔진을 만들 수 있을까” 브레인스토밍 자료**에 더 가깝다.

# 공개 자료에서 내가 직접 다시 확인한 핵심

## 1. Anima Buddy 소개
직접 확인된 핵심 문구:
- Buddy는 Figma 안에서 작동하는 AI design agent로 소개됨
- `create frames`, `use your components`, `apply variables`, `set up auto layout`, `build variants`, `reorganize pages`
- `No terminal. No IDE. No API keys or config files.`
- `Your design system, built in`
- `Choose your model`
- `select any screen`, `works from canvas context`

즉 여기서 확실한 건:
- Buddy는 분명 **canvas-native**
- 분명 **design-system-aware**
- 분명 **agentic action**을 강조한다

## 2. Figma 플러그인 시스템 글
직접 확인된 핵심:
- iframe은 sandbox 역할
- cross-origin iframe은 격리됨
- 메시지 전달 외 직접 접근 불가
- 플러그인 시스템은 문서 접근 가능한 부분과 브라우저 API 가능한 부분이 분리된다

즉, 우리가 말했던
- `plugin code`
- `iframe UI`
- `message passing`
구조는 **확실한 사실**이다.

## 3. `figma/ai-plugin-template`
직접 확인된 핵심:
- iframe 안에서 `figmaAPI.run(...)` 방식으로 코드 실행 요청 가능
- 함수는 stringified 되어 plugin으로 전달됨
- plugin 쪽에서 eval 비슷한 방식으로 실행됨
- 결과는 JSON-serializable 해야 다시 postMessage로 돌아올 수 있음
- OpenAI API key를 앱 서버/웹 앱 쪽에서 사용하게 되어 있음

이건 굉장히 중요해.
왜냐하면 이 템플릿은 “AI 플러그인이 실제로 어떻게 생길 수 있는가”의 **실제 레퍼런스**이기 때문이야.

# 종합 결론

## 확실히 말할 수 있는 것
- Buddy는 Figma 안에서 실제 캔버스 액션을 하는 AI agent로 포지셔닝된다.
- Figma 플러그인 구조상, Buddy도 높은 확률로
  - 문서 접근 가능한 플러그인 코드
  - 네트워크 가능한 UI iframe
  - 둘 사이 메시지 전달
  구조를 가진다.
- design system, components, variables, variants를 주요 가치로 내세운다.
- 단순 채팅이 아니라 `read -> plan -> act` 성격이 강하다.

## 아직 추정인 것
- Buddy의 실제 payload
- 실제 시스템 프롬프트
- 실제 실행 포맷이 codegen인지 structured action인지
- 실제 retry / caching / transport 방식
- 실제 보안 토큰 구조

## xbridge에 가장 유의미한 시사점
자료를 다 합치면, xbridge는 다음 방향으로 가는 게 맞다.

1. `Context Model` 강화
2. `Action Plan` 계층 도입
3. `Executor + Verifier` 분리
4. `Design-system-aware`를 핵심으로
5. 채팅보다 `작업 로그 + 결과 요약 + 후속 액션` 중심 UX
